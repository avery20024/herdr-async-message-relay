# v0.10.1

## Highlights

- **Cancel queued messages:** `hrelay cancel --msg msg-ID` cancels a `queued` message so it is never delivered. The daemon exposes `POST /v1/messages/{id}/cancel`; only messages in the `queued` state can be canceled — `dispatching`, `submitted`, and `uncertain` messages return a 409 error. Canceled messages are retained in history with state `canceled` and are excluded from delivery.
- **Automatic schema migration:** existing databases gain a `canceled` state via an incremental migration applied on first startup. No manual action is required; the migration is a no-op on fresh installs.

## Upgrade and compatibility

1. Update the CLI and restart the worker (`hrelay service restart`) so the daemon binary picks up the new state and endpoint.
2. The schema migration runs automatically on first startup. The upgrade is safe on a live database; it uses a table rename and is wrapped in a transaction.
3. The `hrelay cancel` command requires a worker on v0.10.1 or later. Running `hrelay cancel` against an older daemon returns "未知指令".
4. No existing message state is affected by the upgrade; `queued`, `submitted`, and `uncertain` messages continue as before.

## Known limits

- Only `queued` messages can be canceled. If you need to suppress delivery of a `dispatching` or `submitted` message, the message is already in the delivery pipeline; wait for it to settle to `submitted` or `uncertain` and handle it at the application level.
- Canceled messages are not purged automatically. They remain in the database as history and appear in `hrelay list --state canceled` output.
